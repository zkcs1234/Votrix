# Competition release runbook — candidate only, NO-GO

This is a reviewable plan, not authorization to execute against a hosted candidate or production. No target hostname, backup, RPO/RTO, operator assignment or approval is currently confirmed.

## Preconditions and signoff

The release owner assigns database, recovery, security, infrastructure and QA owners. Each signs the corresponding gate below. Record candidate source hashes, Node/package-lock versions, artifact digests, target identity, approved change window and rollback owner. A Git working tree with prior user changes is not itself a signed deployable artifact: review the entire diff and build a reproducible, immutable candidate through the approved release process. Never reset this workspace to manufacture a clean baseline.

1. **Database owner:** approved direct read-only SQL catalog/ledger access; complete schema, validated constraints, indexes, trigger/function bodies and owners, SECURITY DEFINER search paths, RLS/ACLs and dependencies, including election/polling and historical inventories. Record applied migration IDs/checksums. REST observations do not establish these facts. Compare the target with `baseline.json` and the existing preflight catalog script. Produce a target-specific diff; do not infer an exact diff from absent REST relations.
2. **Recovery owner:** identify backup provider/ID/time/consistent point, retention/PITR coverage, encryption/location/access, restoration procedure, storage assets and signing/configuration/role requirements. Obtain explicit numeric RPO/RTO and operator signoff. Restore the full approved backup to a separately approved isolated target; reconcile all modules, accounts/provider schemas, assets and immutable competition histories. Local sparse fixture restores are supporting evidence only.
3. **Security/QA owners:** approve isolated hosted URLs and dedicated organizer, two judges, independent reviewer, outsider and public test contexts. Supply credentials through approved secret channels. Exercise real login, refresh/rotation, logout/revocation, cookie flags, role/resource denial, CSRF, trusted/untrusted CORS, profile/password gates and hosted PostgREST. Run every workflow and privacy/correction test against the immutable candidate.
4. **Infrastructure owner:** confirm actual instance count and rolling-restart routing; enforce a trusted proxy boundary. `app.js` currently trusts one hop: externally supplied forwarding headers must be overwritten by that hop and direct API ingress restricted. Do not assume Render configuration proves actual topology. Review shared quotas and relay WSS/network isolation/availability, secret rotation, monitoring and outage behavior.
5. **Capacity owner:** approve supported roster/panel/criteria/round and traffic envelope. Retain 100 entrants, five rounds, ten judges/round, ten majors, five equal minors, 12,000 targets/round and 10 MiB exports unless separately reviewed evidence changes the bounds. Measure peak memory, concurrent exports, DB pool limits/lock waits/timeouts, recursive carry, campus NAT/tabs/autosave/public polling and 429 recovery under the hosted envelope.

## Separately authorized candidate sequence

1. Verify target identity and recoverable backup, then obtain explicit permission for candidate migrations/writes. Schedulers/mail/uploads stay disabled or isolated until individually approved.
2. Establish actual reviewed 100–102 prerequisites and ledger. Plan only missing forward migrations in order **103 → 104 → 105 → 106 → 107 → 108**, with exact recorded hashes and transactional/error-stop tooling. Do not replay earlier definitions over later guards. Stop on any unexpected ledger/checksum/catalog/history difference. Migration lock-duration and recovery tolerances must be agreed before execution.
3. Capture before/after lossless record inventories and catalog evidence; compare IDs, values, locks, timestamps, snapshots, current heads, calculations, qualifications and publication lineage. Never recalculate history to reconcile it. Release owner signs migration acceptance.
4. Deploy the approved API/UI candidate with native gates initially disabled, except retain the child ambiguity guard on any populated native target. Verify default legacy/election/polling routes and health. Configure approved proxy, distributed quotas and optional internal relay; validate TLS, network restriction and secret management without logging secret values.
5. Enable backend prerequisites in order: child contexts, setup, scoring, tabulation, results. Align the four frontend setup/scoring/tabulation/results flags with the same reviewed build/schema. The rate-policy gate and relay settings require separate operational approval. Fail closed if prerequisites/API identity metadata are unavailable; never select an event-wide legacy sheet for native records.
6. Execute hosted smoke/acceptance: parent wizard, one child and five siblings, shared masters, explicit panels/rounds, freeze, default-closed gates, automatic updates, drafts/locks/submit, incomplete privacy, correction/cleared-head/retry behavior, all six methods, deductions/review/finalization, ties/qualification/carry, publication replace/withdraw, anonymous tombstones, actual CSV files and negative cross-role/child reads/writes. Include election/polling regressions and recovery checks. Synthetic JWT/local adapter evidence does not satisfy this step.
7. Test actual authenticated sockets on distinct API instances, unauthorized origins/identities, revocation, reconnect/rejoin, rolling restart, duplicated/delayed/out-of-order/missed hints and broker outage/recovery. Require authoritative reconciliation and score-free recipients. The relay is best effort; define and monitor acceptable stale-view latency.
8. Record evidence, incident thresholds and signed approvals. Ask the user for release authorization only after the candidate and every required gate are reviewable and passing. Unresolved P0 gates force **NO-GO**.

## Monitoring and stop criteria

Operations must establish numerical error/429/latency/lock-wait/memory thresholds, collection and alert routing before release; none is currently approved. Monitor API authorization/CSRF failures without score/token logging, SQL timeout/connection pressure, memory/export rejections, relay connection/reconnect/queue pressure, authoritative refetch failures and stale current-source/publication status. Health checks alone do not prove relay delivery or schema compatibility.

Stop activation or acceptance on historical mismatch, permission/privacy leak, missing required current head, stale sources being finalized/published/exported, changed sibling revision, unapproved migration/flag, uncontrolled forwarding headers, exhausted quota, resource saturation, lost recovery evidence or failed transport reconciliation. Preserve incident evidence and contact the assigned owners.

## Safe rollback and recovery

Disable affected results/tabulation/scoring frontend/API gates and communicate unavailability; retain additive tables, immutable history, current-head/qualification protections and the populated-child ambiguity boundary. Do not drop tables, replay old RPC definitions, fabricate completion, rewrite frozen rules, clear heads as a workaround or promise legacy fallback for native records. Feature rollback does not repair data corruption or automatically withdraw an approved published edition.

If data loss/corruption is suspected, the recovery owner obtains separate permission to stop writes and restore/cut over. Restore to isolation first, reconcile acknowledged work after the backup and all account/election/polling/assets/native history, then obtain explicit cutover approval. See the Phase 7 recovery runbook. No production restore is authorized by Phase 9.
