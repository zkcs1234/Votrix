# Prioritized competition implementation plan — proposal only

Audit date: **October 12, 2026**. This plan is based on [findings F-01–F-23](03_GAPS_BUGS_AND_SECURITY_FINDINGS.md), the [control inventory](02_FEATURE_AND_BUTTON_AUDIT.md), [arithmetic review](04_SCORING_AND_TABULATION_REVIEW.md) and [realtime traces](05_REALTIME_SYNC_REVIEW.md). **Nothing in this plan has been implemented.** No new SQL file, application code change, new production test or deployment was made.

The existing architecture is sufficient for the initial repairs: Express/Supabase RPCs, exact shared arithmetic, native authorized WebSocket invalidations and authoritative HTTP refetch. Replacing the application, calculation methods or transport is not the proposed starting point. Changes to competition policy require explicit agreement.

## Dependency order and approval decisions

1. Preserve the current working tree and test evidence; inventory the target schema/ACLs read-only. Confirm which migration versions are actually installed. User confirmation that 097 ran is not proof that all current functions through 099 are installed.
2. Approve the small set of ambiguous business rules: championship field after elimination, pre-scoring setup revision, primary contestant vs input gates, submission window, and ordinary judge results visibility. Existing normalization, aggregation methods, shared cutoff ties and division setting remain unchanged unless explicitly approved otherwise.
3. Fix authorization boundaries and championship eligibility before using real event data. Add narrow regression tests for these substantive defects.
4. Restore complete live/review invalidation, ordered requests and reconnect/fallback behavior. Test with real disposable organizer/judge/reviewer accounts.
5. Complete atomic source validation for freeze/publication, then correct manual/results/report/control inconsistencies.
6. Execute the actual twelve-scenario E2E matrix on a disposable deployment, including direct DB isolation, concurrency, shared-network capacity and official exports. Production release follows verified acceptance, not just green mocked suites.

## Quick fixes versus transactional/infrastructure work

**Focused quick fixes:** nested service event checks; exact trusted Origin policy; reason/confirmed unlock contract; scoped invalidation handlers; footer route; readOnly/catch/allSettled feedback; report filtering/null formatting; stale test wording. These still require actual boundary tests.

**Coordinated correctness work:** championship eligible field, manual scope, full canonical freeze inputs, atomic publication freshness, protected setup revisions and auth/reconnect convergence. Source review and concurrency tests are required before rollout.

**Conditional infrastructure work:** direct DB ACL/RLS based on actual inventory; multi-process delivery only if deployed topology requires it. Do not run migration files merely because they exist or replay 097 after it already ran; additive repair migrations need review, disposable testing and a clear application/database rollout order.

## Release gates

All P0 and applicable P1 findings must have reproducible acceptance evidence. Execute [07](07_END_TO_END_TEST_PLAN.md) with a disposable migrated database, organizer, scoped judges and appointed reviewer, retaining sanitized request/status/source-version evidence. Back up official history before any approved production migration. Deploy compatible database changes before dependent app paths; verify readiness endpoint/schema contracts before admitting scoring traffic. Rollback must preserve rule/submission/result history and must not re-enable token storage or unprotected historical mutation.
